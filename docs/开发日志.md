## 001 2026-10-21 同步仓库并修复真机 scan 断流

### 背景

准备真机实测。Windows 侧仓库在 `feat/turn-speech-and-docs`，WSL 侧停在
`feat/offline-closed-loop-demo`（`c3e4cb5`）且有 61 个未提交改动。
先把两边统一，再验证真机链路，避免"测的不是正在维护的那份代码"。

### 1. 仓库同步

**做法**：以 Windows 仓库为源，WSL 侧用 Git 切换，而不是直接覆盖文件。

| 步骤 | 命令 | 结果 |
|---|---|---|
| 备份未提交改动 | `git diff > ~/go2_backup/wsl-uncommitted-*.patch` | 158 KB 补丁 |
| 备份分支 | `git branch -f backup/wsl-before-sync-20261021 HEAD` | 保留 `c3e4cb5` |
| 旧文档另存 | `cp docs/*.md ~/go2_backup/old-docs/` | 7 份 |
| 加临时远端 | `git remote add win /mnt/d/.../go2_official_ws/.git` | 只读本地路径 |
| 切换分支 | `git checkout -B feat/turn-speech-and-docs win/feat/turn-speech-and-docs` | HEAD = `244d6bb` |

**踩坑**：`git checkout` 两次被拒，分别因为

1. 未跟踪文件会被覆盖 —— 先 `diff` 确认 11 个文件与 Windows 侧**逐字节一致**才删；
2. 已跟踪文件有修改 —— 补丁已备份，`git reset --hard` 后再切。

**判断依据**：`diff -r --strip-trailing-cr` 排除行尾差异后，`src/` 与 `tools/`
只剩 `__pycache__` 不同，说明 WSL 独有的代码改动早已包含在 Windows 侧提交里，
删除未跟踪文件不会丢代码。

### 2. 修复 WSL 下选错网卡

**现象**：`scripts/setup.sh` 默认取默认路由网卡。WSL 镜像模式下默认路由是
Wi-Fi（`eth1 172.16.49.x`），而接狗的是 `eth7 192.168.123.99`。
选错不会报错，只会表现为"`ping` 通、`ros2 topic list` 全空"。

**改动**：`deploy/go2_env.sh` 增加一级选择——先用 `ip route get <狗地址>`
取内核实际出包的网卡，再退回默认路由，最后退回 `enp3s0`。

```bash
GO2_DOG_IP="${GO2_DOG_IP:-192.168.123.161}"
if [ -z "${GO2_IFACE:-}" ] && command -v ip >/dev/null 2>&1; then
  GO2_IFACE="$(ip route get "$GO2_DOG_IP" 2>/dev/null |
    awk '{for (i = 1; i < NF; i++) if ($i == "dev") {print $(i + 1); exit}}')" || GO2_IFACE=""
fi
```

**踩坑（我自己引入又修掉的）**：第一版写成 `export GO2_DOG_IP`（不带值）。
bash 的这种写法会把**调用前的环境变量重新导入**，反而覆盖掉上面算好的默认值。
改成 `export GO2_DOG_IP="${GO2_DOG_IP}"`。

**验证**：

```text
$ source scripts/setup.sh
[go2_env] WS=/home/seven/go2_official_ws SITES=... IFACE=eth7 DOG=192.168.123.161
$ printenv GO2_IFACE
eth7
```

### 3. 真机阻塞问题：点云时间戳落后 295 秒

**现象**：

```text
/utlidar/cloud_deskewed  → 约 13.9 Hz，有数据
/scan                    → 一帧都没有
```

`pointcloud_to_laserscan` 日志：

```text
Message Filter dropping message: frame 'odom' at time 1792552135.701
for reason 'the timestamp on the message is earlier than all the data in the transform cache'
```

**定位过程**（没有靠猜）：

1. 先怀疑 TF 断链（`odom → base_footprint`），但 `odom_bridge` 起来后仍然全丢；
2. 日志里"earlier than all the data"说明不是"缺变换"，而是**时间对不上**；
3. 用 rclpy 直接采样收发时刻，算出真实偏差：

```text
sport  stamp=1792552316.362 rx=1792552611.028 lag=+294.666s
cloud  stamp=1792552316.354 rx=1792552611.032 lag=+294.677s
```

两个话题偏差一致（约 295 s），确认是**机器狗自己的时钟**慢，不是某个节点的问题。

**为什么离线验收测不出来**：`tools/offline_demo/fake_go2*.py` 全部用
`self.get_clock().now()` 打时间戳，假狗与本机同源，永远不会有偏差。

**改动**：

- 新增 `src/go2_patrol_driver/go2_patrol_driver/cloud_time_sync.py`
  —— 订阅 `/utlidar/cloud_deskewed`，按"接收时刻 − 消息时刻"平滑修正时间戳，
  转发到 `/utlidar/cloud_deskewed_ros`；
- `perception.launch.py` 把 `pointcloud_to_laserscan` 的 `cloud_in`
  改到校正后的话题，原始话题保留作旁路；
- `setup.py` 注册 `cloud_time_sync` 入口；
- 新增 `test/test_cloud_time_sync.py`（6 个用例）。

修正策略（`next_offset`）：

| 情况 | 行为 | 原因 |
|---|---|---|
| 第一帧 | 直接对齐 | 295 s 的偏差不能靠几十帧慢慢追 |
| 偏差跳变 > 5 s | 直接对齐 | 狗重启/改时钟后要立刻恢复 |
| 正常帧 | 每帧只追 20% | 单帧抖动不写进 TF，避免时间倒流 |
| 偏差 > 86400 s | 不改，原样转发 | 明显异常的帧不污染时间轴 |

> 这里只改了**感知输入**，没有改动 `odom_bridge`（它本来就用本机时钟），
> 因此 Nav2 的时间轴保持单一来源。

## 002 2026-10-21 真机安全联锁实测（站立待机，零位移）

### 背景

代码里有一层"没有新鲜 `/scan` 就停车"的保护，但离线假狗永远有点云，
这条分支在离线环境里从未被真正走过。真机上必须确认它**不是静默失效**。

### 测试前提

| 项目 | 状态 |
|---|---|
| 机器狗姿态 | 四腿站立待机，`mode: 0`，`body_height: 0.317 m` |
| 速度 | `~1e-8 m/s`（静止） |
| 电池 | SOC 44%，28.47 V |
| 温度 | NTC 44 / 39 °C |
| 周围 | 平地，无人靠近 |
| 限速参数 | `max_linear=0.15`、`max_angular=0.3`（临时压低） |
| 遥控器 | 在手，可随时接管 |

### 做法

1. 只启动 `driver.launch.py`（odom / battery / twist / tf 守护），
   **不启动** Nav2 与巡检；
2. 不发任何非零速度，只发一条**全零** `/cmd_vel`，用来触发驱动的判断分支；
3. 同时用独立节点监听 `/api/sport/request`，记录实际发出的 `api_id`。

### 证据

驱动日志：

```text
[go2_twist_bridge] 没有新的 /scan（超过 1.0s 或从未收到），按安全策略停车：
检查机载点云 /utlidar/cloud_deskewed 与 pointcloud_to_laserscan；
确认无雷达的台架才允许把 require_scan 设为 false
```

请求监听（12 秒窗口）：

```text
api_id counts: {1003: 3}
MOVE(1008) sent: 0
STOP_MOVE(1003) sent: 3
```

机器狗状态（同一时段）：

```text
velocity:
- -4.7987662732396075e-09
- -1.0920943260828153e-08
```

### 结论

- 无扫描时**只刹车、不前进**：`MOVE(1008)` 计数为 0；
- 3 次 `STOP_MOVE` 分别来自"收到 `/cmd_vel` 即停"与看门狗补刹车；
- 机器狗全程未移动（速度在 1e-8 量级，属于噪声）。

### 踩坑

- `ros2 topic pub` **不支持** `--no-daemon`（`ros2 topic echo/list` 才支持），
  加了会直接报 `unrecognized arguments`；
- `ros2 node list` 有时在节点刚起时返回空，等 3~5 秒或用 `--no-daemon` 更稳；
- 在 bash 里 `export GO2_IFACE=...; echo "$GO2_IFACE"` 之所以看起来为空，
  是本机 shell 的引号处理问题，`printenv GO2_IFACE` 才能看到真实值。

### 遗留

- [ ] 本次**没有做任何位移测试**。下一步若要测运动，应按第 9 节：
  平地、留空 2 m、遥控器在手、先把 `max_linear` 压到 0.15，
  并且只在一个方向、一米以内做"走—停"验证；
- [ ] 电池 44%，长距离建图/导航前先充电。

### 追加：文档订正

同一提交里把 `docs/真机部署与使用手册.md` 4.3 节的频率表按实测改了：
`/lf/sportmodestate` 50 Hz → **20 Hz**，补充 `/scan` 与点云同频的判据，
并加了"`/scan` 为 0 而点云有频率 → 先查时间戳"的指向。

### 追加：提交前复测（冷启动）

重启 WSL 后不带任何手工步骤，直接起感知链路：

```text
[cloud_time_sync] 点云时间戳对齐已启动：/utlidar/cloud_deskewed -> /utlidar/cloud_deskewed_ros
[cloud_time_sync] 点云与电脑时钟相差 +295.2s，开始按本机时钟重打时间戳

$ ros2 topic hz /scan
average rate: 14.794 → 15.110（连续 6 次采样，稳定）

$ grep -c "dropping message" /tmp/final_perc.log
0
```

偏差仍为 +295.2 s（说明狗没有自动对时），但对齐后**丢帧数为 0**，
证明修复不依赖"把狗时钟改对"，每次起机都会自动收敛。

> 这也说明：**不要**试图去改机器狗的时钟（多数固件不开放），
> 在控制端做时间戳归一才是可复现的做法。

## 003 2026-10-21 巡检前置条件与建图能力确认

### 问题

用户问："想测巡检，是不是需要建图？"

### 结论：必须先建图，三步不能省

代码里巡检不是"按坐标盲走"，而是
`地图 → AMCL 定位 → Nav2 规划 → 航点下发`：

| 依赖 | 代码位置 | 缺了会怎样 |
|---|---|---|
| 静态地图 | `navigation.launch.py` → `nav2_bringup` 的 `map:=` | `map_server` 起不来，Nav2 无法规划 |
| AMCL 定位 | `nav2_params.yaml` 的 `amcl` 段（`global_frame_id: map`） | `map→odom` 不存在，`/amcl_pose` 无数据 |
| 航点坐标 | `waypoints.yaml`（map 坐标系，米/弧度） | 目标点落到墙里或原点，导航必然失败 |

**关键证据**：仓库里 `src/go2_patrol_bringup/maps/` 目前只有 `README.md`，
**没有任何 `.yaml`/`.pgm`**。`deploy/site.example/map.pgm` 只是示例资产，
不是真机地图。所以现在直接跑 `patrol.launch.py` 一定起不来。

另外 `amcl` 段是 `set_initial_pose: false`，意味着开发机手动启动时必须
在 RViz 里点一次 `2D Pose Estimate`；只有走站点部署
（`apply_site.sh` + `render_site.py`）才会写死固定起点并置为 `true`。

### 本次验证（狗站立待机，零位移）

只启动建图链路，确认它具备出图能力：

```text
$ ros2 launch go2_patrol_bringup mapping.launch.py

$ ros2 node list
/base_link_to_lidar
/cloud_time_sync
/go2_battery_bridge
/go2_odom_bridge
/go2_tf_chain_guard
/go2_twist_bridge
/pointcloud_to_laserscan
/slam_toolbox          ← 8 个节点全起

$ ros2 topic echo /map --once --field info
resolution: 0.05000000074505806
width: 65
height: 66
origin: {x: -1.460, y: -3.274, z: 0.0}
```

起点附近已生成 65×66 的栅格（约 3.25 m × 3.3 m），说明
`点云 → /scan → slam_toolbox → /map` 整条链通了。

> 注意：这只是"站着不动"产生的局部地图，不是可用地图。
> 真实建图必须**遥控走完整个场地**。

### 正确顺序

1. **建图**：`mapping.launch.py` + 遥控器走完全场 → `scripts/save_map.sh office_floor`
2. **验证地图**：墙线连续、走回起点不错层
3. **单点导航**：`navigation.launch.py map:=...`，RViz 给初始位姿 + 1~2 m 近目标
4. **采点**：`record_waypoint` 采 `home` 和巡检点
5. **跑巡检**：`patrol.launch.py`

### 安全提醒

- 建图阶段**由遥控器控制行走**，本项目只接收数据，不发运动指令；
- 首次建图把 `GO2_MAX_LINEAR` 压到 `0.2` 以下：同一套 launch 会起
  `twist_bridge`，防止误触发时速度过大；
- 建图前确认电池 > 50%。本次实测 SOC 已降到 44%，**建议先充电**。

### 遗留

- [ ] 仓库缺真机地图，建图完成后需提交 `maps/office_floor.yaml` + `.pgm`；
- [ ] `waypoints.yaml` 现在是占位坐标（`(2.0, 0.0)`），必须用
  `record_waypoint` 重新采集，不能直接用于真机。

### 追加：姿态措辞修正

002 里写的"趴卧"不准确。遥测中 `mode: 0`、`body_height: 0.317 m`
符合**四腿站立待机**，已全文改为"站立待机"。

> 仓库根目录的 `image.png` **不是本项目机器狗**，只是参考照片，
> 不能用它推断本机的 `robot_radius`、外形或现场环境。
> 相关参数必须以实际机器实测为准。

### 追加：把 `/map` 导出成图片

新增 `tools/save_map_png.py`，在没有 RViz 或需要存档时把
`nav_msgs/OccupancyGrid` 直接渲染成 PNG：

```bash
python3 tools/save_map_png.py /tmp/map.png --scale 12 --legend
```

实现要点（踩过的坑）：

- `/map` 是 **latched（transient_local）** 话题，用默认 QoS 订阅收不到
  已经发布过的那一份，必须显式设 `DurabilityPolicy.TRANSIENT_LOCAL`；
- 栅格原点在**左下**，PIL 的行从上到下，必须 `np.flipud`，否则地图上下颠倒；
- PIL 自带位图字体只支持 latin-1，图例写中文会抛 `UnicodeEncodeError`，
  所以图例用英文。

**实测输出（狗静止 26 s 后）**：

```text
尺寸 51x62 @ 0.050 m/cell
原点 (-0.559, -3.113)
占用 4，空闲 32，未知 3126
```

图上只有一条从当前位置扫出去的白色扇形和 4 个黑点，占用率约 0.13%。

**结论**：这证明 `点云 → /scan → slam_toolbox → /map` 链路通了，
但**不是可用地图**——机器人没移动，地图无法扩展也无法闭环。
建立可用地图必须遥控走完整个场地。

## 004 2026-10-21 建图链路三个根因修复 + 建图期运动闸门

### 背景

003 之后遥控走位建图，`/map` 呈**放射状散点**，墙线不闭合。逐层量数据，
定位到三个独立 bug，外加一个建图期的**安全缺口**。

### Bug 1：每帧 10 000 个全零填充点

**证据**：`/utlidar/cloud_deskewed` 每帧固定 10 606 点，前 **10 000 个坐标精确为
`(0,0,0)`**，真实回波 500–600 个排在尾部。消息 `is_dense=True`，没有 NaN，
所以下游没有任何过滤会拦下它。

**后果**：`pointcloud_to_laserscan` 把 `(0,0,0)` 当成"距离 0 的障碍"，
裁到 `range_min` 后在狗脚下糊出一圈**假墙**（实测 `/scan` 最小距离 0.15 m）。

**修复**：`cloud_time_sync.py` 新增 `compact_points()` / `keep_mask()`，
按 `point_step` 用 numpy 向量化重打包，参数 `drop_zero_points=True`、
`zero_epsilon=1e-4`。

### Bug 2：L1 是非重复扫描（放射状的真正根因）

**证据**（30 帧实测，每帧 1 434 点）：

- 单帧方位覆盖 **242 / 360**；
- 相邻帧方位重叠只有 **65%**；
- 连续 25 帧 `/scan` 统计：723 个 bin 里只有 **90 个**在 ≥80% 的帧里有值；
- 这 90 个 bin 的距离标准差中位数 **0.150 m（相对 37%）**。

**后果**：同一方位在不同帧里时有时无、数值来回跳 → `slam_toolbox` 的
`map->odom` 原地反复修正 → 地图呈放射状。

**修复**：新增 `cloud_accumulator` 节点，把最近 10 帧按 TF 变换到当前
`base_footprint` 后合并再发 `/scan`。两个关键细节：

- 点云 stamp 比 `odom→base_footprint` 新约 2 ms，直接查 TF 必定
  `extrapolation into the future`；`lookup_with_grace()` 按 0.02 s 步长回退最多 0.1 s；
- 静止时必须用新时间戳重发缓存，否则 `twist_bridge` 的 `require_scan` 会判成断流；
  位姿门限 `min_travel_distance=0.02` / `min_time_interval=0.03` 防止原地重复叠加。

**修复后实测**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 稳定 bin（≥80% 帧有值） | 90 / 723 | **426 / 723** |
| 距离标准差（中位） | 0.150 m | **0.041 m** |
| 相对标准差 | 37% | **9.8%** |
| 点云空点 | 10 000 / 帧 | **0** |
| `/scan` 最小距离 | 0.15 m（假墙） | 0.31 m（真实） |

### Bug 3：TF 被 7 个 `static_transform_publisher` 污染

**证据**：反复重启后 `pgrep -c -f static_transform_publisher` = **7**，
`/tf` 里同一条 `base_link→utlidar_lidar` 叠了 7 份，地图直接冻住不更新。

**修复**：新增 `scripts/stop_mapping.sh`，三轮回溯清理（launch → 子节点 → 孤儿）。
**踩坑**：脚本最初用 `bash -lc` 调用时，命令行本身含匹配关键字，
`pkill -f` 会把父 shell 一起杀掉，表现为"只杀一半、脚本静默退出"。
现改为 `ps -eo pid=,args=` 取列表并排除 `bash/sh/grep/pgrep/ps` 搬运工。

### 安全缺口：建图期 `twist_bridge` 仍在收 `/cmd_vel`

**问题**：`mapping.launch.py` 整包 include 了 `driver.launch.py`，
除建图要用的 `odom_bridge` / `battery_bridge` / `tf_chain_guard` 外，
**`twist_bridge` 也常驻**。它只要收到一帧 `/cmd_vel`，就会翻成官方
`MOVE(1008)` 让狗起步——RViz 误点 2D Goal Pose、残留 teleop、别的节点误发都算。
"建图只用遥控器"这个约定此前**没有代码强制**。

**修复**：加一层默认开启、建图时显式关闭的运动闸门。

## 009 2026-10-22 MOVE 指令"返回成功但不走"的根因

### 现象

用 `tools/straight_move.py` 下发 0.5 m 直行（0.08 m/s），
`MOVE(1008)` 每帧都返回 `code=0`，但狗只挪 2–9 cm。
同期遥控器推杆能正常走。

### 根因 A：重复的 driver 进程抢 TF，导致 /scan 断流

`ps` 显示同时存在两套 `odom_bridge` / `twist_bridge`
（PID 1124–1130 与 2345–2351）。两个 `odom_bridge` 抢发
`odom→base_footprint`，`cloud_accumulator` 查 TF 时命中旧的一份，
报"查不到 base_footprint <- odom"后丢帧 → `/scan` 停 →
`twist_bridge` 的 `require_scan` 判成断流 → **持续发 STOP_MOVE**。
这是"指令成功但不动"的直接原因之一。

清理后验证：

| 项 | 值 |
|---|---|
| `go2_patrol_driver/lib` 进程数 | 6（odom/battery/twist/tf_guard/cloud_time_sync/cloud_accumulator） |
| `pointcloud_to_laserscan` | 1 |
| `/scan` | 16.3 Hz |
| `/odom` / `/lf/sportmodestate` | 22 Hz |

**踩坑**：按 `grep "go2_patrol_driver/lib"` 杀进程会连带杀掉感知节点
（`cloud_time_sync` / `cloud_accumulator` 装在同一目录）。要么按
`ros2 launch` 父进程整组重启，要么杀完必须核对进程数。

### 根因 B：0.08 m/s 低于 Go2 的步态启动阈值

单独测 MOVE 的位移/速度关系（每次 1.2 s）：

| 指令速度 | 1.2 s 实际位移 | 反馈速度 |
|---|---|---|
| 0.08 m/s | ≈0（多次失败） | 0 |
| 0.15 m/s | 0.034 m | 0 |
| **0.25 m/s** | **0.152 m** | 0 |

**结论**：Go2 的 `MOVE` 有最小启动速度，低于它时服务端返回成功但不出步。
官方示例用 `Move(0.3, 0, 0.3)`，与此一致。

**重要**：`sportmodestate.velocity` 行走时**仍然恒为 0**，
不能拿来判断"是否在动"，只能看 `position` 差分或 `/odom`。

### 附带发现

- 0.25 m/s 实测只跑到约 0.13 m/s（0.152 m / 1.2 s），约为指令值的 50%；
  再叠加 `twist_bridge` 的 `slow_distance=0.60` 会减半，实际可能只剩 0.03 m/s。
  短距离测试应取 0.25 以上，或临时调小 `slow_distance`。
- USB 网卡（`VID_0BDA&PID_8152`）当天**两次从 USB 总线消失**
  （`Get-PnpDevice` 状态 `Unknown`，PnP 重新枚举返回"常规故障"），
  只能物理换口。换口后恢复，RTT 1–2 ms。

### 遗留

- [ ] 需确认 Go2 最小可执行速度的确切值（在 0.15 与 0.25 之间），
      否则导航参数设得过低会出现"规划成功但不动"；
- [ ] `sportmodestate.velocity` 恒 0 需单独记录，到位判据必须用
      `position` 或 `/odom`。

| 4 s | 0.41 m |
| 5 s | **0.41 m** |

**结果**：距离稳定在 0.41 m，**没有继续靠近**，也未触碰。

这证明：

1. 前置判断是**逐帧**生效的，不是只在第一次触发；
2. `twist_bridge` 没有把 `MOVE` 透传下去，而是持续转换成 `STOP_MOVE`；
3. 6 秒硬推也无法让机器狗挤过安全线。

### 测试中发现的限制（重要）

**`MOVE` 的 `x` 为负值（后退）在这台机器狗的待机模式下不生效。**

下发 −0.30 m/s 两秒：后方距离 0.88 → 0.89 m（几乎不动），
前方反而 0.49 → 0.45 m（轻微前移）。所以"退后"不能靠负速度，
只能靠"转向 + 前进"或先切到行走模式。

### 关于 `sportmodestate.imu_state.rpy` 字段顺序

排查过程中一度误判"转向指令不生效"，根因是**这台 Go2 的 `rpy` 顺序特殊**：

```text
实测 rpy = [-2.5, 3.6, -75.7]（度）
四元数 [x,y,z,w] 算出的 yaw = -2.5°
→ rpy[0] 才是 yaw，rpy[2] 是另一个物理量
```

短转向实验（`z=0.4`）中 `rpy[0]` 与四元数 yaw **同步变化**（−2.5 → −1.2），
进一步确认。`odom_bridge` 用四元数计算 yaw 是**正确**的，不需要改。

### 结论

| 验证项 | 结果 |
|---|---|
| `/cmd_vel` → `MOVE(1008)` 转换 | ✅ |
| 前方接近时减速 | ✅ |
| 前方 0.41 m 处停车 | ✅ 未触碰 |
| 急停后持续硬推仍保持停止 | ✅ |
| 后退（负 `x`） | ❌ 待机模式不支持 |
