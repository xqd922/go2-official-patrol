## 001 2026-10-21 同步仓库并修复真机 scan 断流

### 背景

准备真机实测。Windows 侧仓库在 `feat/turn-speech-and-docs`，WSL 侧停在
`feat/offline-closed-loop-demo`（`c3e4cb5`）且有 61 个未提交改动。
先把两边统一，再验证真机链路，避免"测的不是正在维护的那份代码"。

### 1. 仓库同步

**做法**：以 Windows 仓库为源，WSL 侧用 Git 切换，而不是直接覆盖文件。

| 步骤 | 命令 | 结果 |
|---|---|---|
| 备份未提交改动 | `git diff > ~/go2_backup/wsl-uncommitted-*.patch` | 158 KB 补丁 |
| 备份分支 | `git branch -f backup/wsl-before-sync-20261021 HEAD` | 保留 `c3e4cb5` |
| 旧文档另存 | `cp docs/*.md ~/go2_backup/old-docs/` | 7 份 |
| 加临时远端 | `git remote add win /mnt/d/.../go2_official_ws/.git` | 只读本地路径 |
| 切换分支 | `git checkout -B feat/turn-speech-and-docs win/feat/turn-speech-and-docs` | HEAD = `244d6bb` |

**踩坑**：`git checkout` 两次被拒，分别因为

1. 未跟踪文件会被覆盖 —— 先 `diff` 确认 11 个文件与 Windows 侧**逐字节一致**才删；
2. 已跟踪文件有修改 —— 补丁已备份，`git reset --hard` 后再切。

**判断依据**：`diff -r --strip-trailing-cr` 排除行尾差异后，`src/` 与 `tools/`
只剩 `__pycache__` 不同，说明 WSL 独有的代码改动早已包含在 Windows 侧提交里，
删除未跟踪文件不会丢代码。

### 2. 修复 WSL 下选错网卡

**现象**：`scripts/setup.sh` 默认取默认路由网卡。WSL 镜像模式下默认路由是
Wi-Fi（`eth1 172.16.49.x`），而接狗的是 `eth7 192.168.123.99`。
选错不会报错，只会表现为"`ping` 通、`ros2 topic list` 全空"。

**改动**：`deploy/go2_env.sh` 增加一级选择——先用 `ip route get <狗地址>`
取内核实际出包的网卡，再退回默认路由，最后退回 `enp3s0`。

```bash
GO2_DOG_IP="${GO2_DOG_IP:-192.168.123.161}"
if [ -z "${GO2_IFACE:-}" ] && command -v ip >/dev/null 2>&1; then
  GO2_IFACE="$(ip route get "$GO2_DOG_IP" 2>/dev/null |
    awk '{for (i = 1; i < NF; i++) if ($i == "dev") {print $(i + 1); exit}}')" || GO2_IFACE=""
fi
```

**踩坑（我自己引入又修掉的）**：第一版写成 `export GO2_DOG_IP`（不带值）。
bash 的这种写法会把**调用前的环境变量重新导入**，反而覆盖掉上面算好的默认值。
改成 `export GO2_DOG_IP="${GO2_DOG_IP}"`。

**验证**：

```text
$ source scripts/setup.sh
[go2_env] WS=/home/seven/go2_official_ws SITES=... IFACE=eth7 DOG=192.168.123.161
$ printenv GO2_IFACE
eth7
```

### 3. 真机阻塞问题：点云时间戳落后 295 秒

**现象**：

```text
/utlidar/cloud_deskewed  → 约 13.9 Hz，有数据
/scan                    → 一帧都没有
```

`pointcloud_to_laserscan` 日志：

```text
Message Filter dropping message: frame 'odom' at time 1792552135.701
for reason 'the timestamp on the message is earlier than all the data in the transform cache'
```

**定位过程**（没有靠猜）：

1. 先怀疑 TF 断链（`odom → base_footprint`），但 `odom_bridge` 起来后仍然全丢；
2. 日志里"earlier than all the data"说明不是"缺变换"，而是**时间对不上**；
3. 用 rclpy 直接采样收发时刻，算出真实偏差：

```text
sport  stamp=1792552316.362 rx=1792552611.028 lag=+294.666s
cloud  stamp=1792552316.354 rx=1792552611.032 lag=+294.677s
```

两个话题偏差一致（约 295 s），确认是**机器狗自己的时钟**慢，不是某个节点的问题。

**为什么离线验收测不出来**：`tools/offline_demo/fake_go2*.py` 全部用
`self.get_clock().now()` 打时间戳，假狗与本机同源，永远不会有偏差。

**改动**：

- 新增 `src/go2_patrol_driver/go2_patrol_driver/cloud_time_sync.py`
  —— 订阅 `/utlidar/cloud_deskewed`，按"接收时刻 − 消息时刻"平滑修正时间戳，
  转发到 `/utlidar/cloud_deskewed_ros`；
- `perception.launch.py` 把 `pointcloud_to_laserscan` 的 `cloud_in`
  改到校正后的话题，原始话题保留作旁路；
- `setup.py` 注册 `cloud_time_sync` 入口；
- 新增 `test/test_cloud_time_sync.py`（6 个用例）。

修正策略（`next_offset`）：

| 情况 | 行为 | 原因 |
|---|---|---|
| 第一帧 | 直接对齐 | 295 s 的偏差不能靠几十帧慢慢追 |
| 偏差跳变 > 5 s | 直接对齐 | 狗重启/改时钟后要立刻恢复 |
| 正常帧 | 每帧只追 20% | 单帧抖动不写进 TF，避免时间倒流 |
| 偏差 > 86400 s | 不改，原样转发 | 明显异常的帧不污染时间轴 |

> 这里只改了**感知输入**，没有改动 `odom_bridge`（它本来就用本机时钟），
> 因此 Nav2 的时间轴保持单一来源。

## 002 2026-10-21 真机安全联锁实测（趴卧状态，零位移）

### 背景

代码里有一层"没有新鲜 `/scan` 就停车"的保护，但离线假狗永远有点云，
这条分支在离线环境里从未被真正走过。真机上必须确认它**不是静默失效**。

### 测试前提

| 项目 | 状态 |
|---|---|
| 机器狗姿态 | 趴卧，`mode: 0` |
| 速度 | `~1e-8 m/s`（静止） |
| 电池 | SOC 44%，28.47 V |
| 温度 | NTC 44 / 39 °C |
| 周围 | 平地，无人靠近 |
| 限速参数 | `max_linear=0.15`、`max_angular=0.3`（临时压低） |
| 遥控器 | 在手，可随时接管 |

### 做法

1. 只启动 `driver.launch.py`（odom / battery / twist / tf 守护），
   **不启动** Nav2 与巡检；
2. 不发任何非零速度，只发一条**全零** `/cmd_vel`，用来触发驱动的判断分支；
3. 同时用独立节点监听 `/api/sport/request`，记录实际发出的 `api_id`。

### 证据

驱动日志：

```text
[go2_twist_bridge] 没有新的 /scan（超过 1.0s 或从未收到），按安全策略停车：
检查机载点云 /utlidar/cloud_deskewed 与 pointcloud_to_laserscan；
确认无雷达的台架才允许把 require_scan 设为 false
```

请求监听（12 秒窗口）：

```text
api_id counts: {1003: 3}
MOVE(1008) sent: 0
STOP_MOVE(1003) sent: 3
```

机器狗状态（同一时段）：

```text
velocity:
- -4.7987662732396075e-09
- -1.0920943260828153e-08
```

### 结论

- 无扫描时**只刹车、不前进**：`MOVE(1008)` 计数为 0；
- 3 次 `STOP_MOVE` 分别来自"收到 `/cmd_vel` 即停"与看门狗补刹车；
- 机器狗全程未移动（速度在 1e-8 量级，属于噪声）。

### 踩坑

- `ros2 topic pub` **不支持** `--no-daemon`（`ros2 topic echo/list` 才支持），
  加了会直接报 `unrecognized arguments`；
- `ros2 node list` 有时在节点刚起时返回空，等 3~5 秒或用 `--no-daemon` 更稳；
- 在 bash 里 `export GO2_IFACE=...; echo "$GO2_IFACE"` 之所以看起来为空，
  是本机 shell 的引号处理问题，`printenv GO2_IFACE` 才能看到真实值。

### 遗留

- [ ] 本次**没有做任何位移测试**。下一步若要测运动，应按第 9 节：
  平地、留空 2 m、遥控器在手、先把 `max_linear` 压到 0.15，
  并且只在一个方向、一米以内做"走—停"验证；
- [ ] 电池 44%，长距离建图/导航前先充电。

### 追加：文档订正

同一提交里把 `docs/真机部署与使用手册.md` 4.3 节的频率表按实测改了：
`/lf/sportmodestate` 50 Hz → **20 Hz**，补充 `/scan` 与点云同频的判据，
并加了"`/scan` 为 0 而点云有频率 → 先查时间戳"的指向。

### 追加：提交前复测（冷启动）

重启 WSL 后不带任何手工步骤，直接起感知链路：

```text
[cloud_time_sync] 点云时间戳对齐已启动：/utlidar/cloud_deskewed -> /utlidar/cloud_deskewed_ros
[cloud_time_sync] 点云与电脑时钟相差 +295.2s，开始按本机时钟重打时间戳

$ ros2 topic hz /scan
average rate: 14.794 → 15.110（连续 6 次采样，稳定）

$ grep -c "dropping message" /tmp/final_perc.log
0
```

偏差仍为 +295.2 s（说明狗没有自动对时），但对齐后**丢帧数为 0**，
证明修复不依赖"把狗时钟改对"，每次起机都会自动收敛。

> 这也说明：**不要**试图去改机器狗的时钟（多数固件不开放），
> 在控制端做时间戳归一才是可复现的做法。

## 003 2026-10-21 巡检前置条件与建图能力确认

### 问题

用户问："想测巡检，是不是需要建图？"

### 结论：必须先建图，三步不能省

代码里巡检不是"按坐标盲走"，而是
`地图 → AMCL 定位 → Nav2 规划 → 航点下发`：

| 依赖 | 代码位置 | 缺了会怎样 |
|---|---|---|
| 静态地图 | `navigation.launch.py` → `nav2_bringup` 的 `map:=` | `map_server` 起不来，Nav2 无法规划 |
| AMCL 定位 | `nav2_params.yaml` 的 `amcl` 段（`global_frame_id: map`） | `map→odom` 不存在，`/amcl_pose` 无数据 |
| 航点坐标 | `waypoints.yaml`（map 坐标系，米/弧度） | 目标点落到墙里或原点，导航必然失败 |

**关键证据**：仓库里 `src/go2_patrol_bringup/maps/` 目前只有 `README.md`，
**没有任何 `.yaml`/`.pgm`**。`deploy/site.example/map.pgm` 只是示例资产，
不是真机地图。所以现在直接跑 `patrol.launch.py` 一定起不来。

另外 `amcl` 段是 `set_initial_pose: false`，意味着开发机手动启动时必须
在 RViz 里点一次 `2D Pose Estimate`；只有走站点部署
（`apply_site.sh` + `render_site.py`）才会写死固定起点并置为 `true`。

### 本次验证（狗趴卧，零位移）

只启动建图链路，确认它具备出图能力：

```text
$ ros2 launch go2_patrol_bringup mapping.launch.py

$ ros2 node list
/base_link_to_lidar
/cloud_time_sync
/go2_battery_bridge
/go2_odom_bridge
/go2_tf_chain_guard
/go2_twist_bridge
/pointcloud_to_laserscan
/slam_toolbox          ← 8 个节点全起

$ ros2 topic echo /map --once --field info
resolution: 0.05000000074505806
width: 65
height: 66
origin: {x: -1.460, y: -3.274, z: 0.0}
```

起点附近已生成 65×66 的栅格（约 3.25 m × 3.3 m），说明
`点云 → /scan → slam_toolbox → /map` 整条链通了。

> 注意：这只是"趴着不动"产生的局部地图，不是可用地图。
> 真实建图必须**遥控走完整个场地**。

### 正确顺序

1. **建图**：`mapping.launch.py` + 遥控器走完全场 → `scripts/save_map.sh office_floor`
2. **验证地图**：墙线连续、走回起点不错层
3. **单点导航**：`navigation.launch.py map:=...`，RViz 给初始位姿 + 1~2 m 近目标
4. **采点**：`record_waypoint` 采 `home` 和巡检点
5. **跑巡检**：`patrol.launch.py`

### 安全提醒

- 建图阶段**由遥控器控制行走**，本项目只接收数据，不发运动指令；
- 首次建图把 `GO2_MAX_LINEAR` 压到 `0.2` 以下：同一套 launch 会起
  `twist_bridge`，防止误触发时速度过大；
- 建图前确认电池 > 50%。本次实测 SOC 已降到 44%，**建议先充电**。

### 遗留

- [ ] 仓库缺真机地图，建图完成后需提交 `maps/office_floor.yaml` + `.pgm`；
- [ ] `waypoints.yaml` 现在是占位坐标（`(2.0, 0.0)`），必须用
  `record_waypoint` 重新采集，不能直接用于真机。
